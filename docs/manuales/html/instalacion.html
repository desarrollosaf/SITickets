1 Qué es el sistema y cómo está armado

Antes de instalar conviene tener claro de qué piezas se compone el sistema y de dónde depende cada una.

Mesa de ayuda (SITickets) es un sistema de dos partes que se ejecutan por separado:

  • Backend — API en NestJS (Node.js), expone todo bajo /api y genera los PDF (dictámenes, cédulas) con Puppeteer/Chromium.
  • Frontend — aplicación Angular compilada a archivos estáticos, servidos por un contenedor nginx propio.

El sistema no trae su propia base de datos: se conecta a bases MySQL que ya existen y son operadas por otras áreas. En total usa cuatro conexiones:

ConexiónPara qué se usaQuién la provee
Por defecto (mesa_ayuda)Toda la operación propia del sistema: tickets, catálogos, usuarios, bitácoraPropia del sistema — el equipo de informática crea este esquema
safPadrón de personal del Congreso (nombre, RFC, dependencia, dirección, departamento) — es de solo lecturaÁrea de Recursos Humanos / Secretaría de Administración y Finanzas
bienesResguardos de equipo de cómputo (número de inventario), solo para servicios fuera de EQUIPO DE CÓMPUTOÁrea de Bienes Muebles
eserviceCatálogo de impresoras arrendadas y nivel de tóner (lectura y escritura, la alimenta un script externo en Python)Sistema eService (PHP/Laravel) existente
Importante Para EQUIPO DE CÓMPUTO, el número de inventario y el trámite de "equipo en mantenimiento"/baja no pasan por la base bienes, sino por una API HTTP real del sistema SIASAF (BIENES_API_BASE_URL). Esa API debe estar accesible desde el servidor donde corra el backend.

2 Requisitos antes de instalar

En el servidor

  • Docker y Docker Compose (v2) — es la forma soportada de correr el sistema, en desarrollo y en producción.
  • Acceso de red saliente, desde el servidor, hacia: el MySQL que aloja las 4 bases, y la API de SIASAF (siasaf.gob.mx).
  • Un dominio o subruta pública detrás de un proxy (por ejemplo https://siasaf.gob.mx/sitickets), con HTTPS.
  • Puertos libres en el host para los dos contenedores (por convención 8087 para el frontend y 3032 para el backend; son configurables).

En las bases de datos

  • Un usuario de MySQL con permisos de lectura y escritura sobre el esquema propio del sistema (el backend crea y actualiza sus tablas solo).
  • Un usuario con permiso de solo lectura sobre saf y bienes.
  • Un usuario con lectura y escritura sobre eservice (ahí escribe el script de monitoreo de tóner).
Nota sobre host.docker.internal Si el MySQL vive en la misma máquina donde corre Docker, el backend se conecta a él por host.docker.internal, no por localhost (localhost dentro del contenedor es el propio contenedor). Si el MySQL está en otro servidor de la red, se usa su IP o su nombre interno.

3 Variables de entorno

Todo lo anterior se configura en un solo archivo: backend/.env. Nunca se sube al repositorio — se copia a mano en el servidor a partir de la plantilla.

cp backend/.env.example backend/.env # y despues se edita backend/.env con los valores reales

Conexión principal y comportamiento del esquema

VariablePara qué sirve
DB_HOST / DB_PORT / DB_NAME / DB_USER / DB_PASSConexión al esquema propio del sistema
DB_SYNCfalse en producción. En true, Sequelize crea/ajusta tablas directo desde el código — solo para desarrollo.
DB_MIGRARtrue en producción. Aplica los .sql de backend/sql/migraciones al arrancar, uno por uno, y nunca repite uno ya aplicado.
SEED_ON_BOOT / SEED_PASSWORDSi la base está vacía, siembra catálogos y el padrón de usuarios con esa contraseña inicial.

Las otras tres conexiones

VariablePara qué sirve
SAF_DB_HOST / _PORT / _NAME / _USER / _PASSConexión de solo lectura al padrón de personal
BIENES_DB_HOST / _PORT / _NAME / _USER / _PASSConexión de solo lectura a resguardos (servicios distintos a EQUIPO DE CÓMPUTO)
ESERVICE_DB_HOST / _PORT / _NAME / _USER / _PASSConexión de lectura y escritura al catálogo de impresoras y lecturas de tóner

Integraciones externas

VariablePara qué sirve
BIENES_API_BASE_URLAPI real de SIASAF para EQUIPO DE CÓMPUTO (consulta de resguardos, ficha técnica, alta/baja de "en mantenimiento")
PYTHON_TONER_API_KEYClave fija que debe enviar el script externo de monitoreo de tóner (header X-Api-Key), no usa sesión de usuario
ANTHROPIC_API_KEY / ANTHROPIC_MODELSolo para el botón "Mejorar redacción" del dictamen de baja. Si se deja vacío, el resto del sistema sigue funcionando; solo ese botón no responde.

Seguridad y sesión

VariablePara qué sirve
JWT_SECRETFirma los tokens de sesión. Generar uno largo y aleatorio: openssl rand -base64 48
JWT_EXPIRESDuración de la sesión (por omisión 8h)
CORS_ORIGINDominio exacto desde el que el navegador puede llamar a la API, por ejemplo https://siasaf.gob.mx

Antes de arrancar en producción Revisa que DB_SYNC=false y DB_MIGRAR=true. Con DB_SYNC=true en un servidor real, el sistema puede intentar modificar tablas directo desde los modelos antes de que corran las migraciones.

4 Despliegue con Docker

  1. Clonar el repositorio en el servidor y entrar a la carpeta del proyecto.
  2. Crear backend/.env a partir de backend/.env.example, con los valores reales (capítulo 3).
  3. Revisar docker-compose.prod.yml: define dos servicios —
    • frontend: compila el Angular (con BASE_HREF=/sitickets/) y lo sirve con nginx en el puerto 8087.
    • backend: compila y corre el NestJS en el puerto 3032, monta backend/storage como volumen (ahí se guardan los PDF de dictamen y cédulas — debe persistir entre despliegues).
  4. Levantar los contenedores:
    docker compose -f docker-compose.prod.yml up -d --build
  5. Revisar el arranque del backend:
    docker logs sitickets-backend --tail 50
    Debe aparecer Migraciones: Esquema al corriente y Nest application successfully started. Si es la primera vez, antes aparecerán las migraciones aplicándose una por una.
Dato util Las migraciones son automáticas e idempotentes: cada vez que se despliega una versión nueva del código, el backend revisa qué archivos de backend/sql/migraciones no se han aplicado todavía y solo corre esos. No hace falta correr nada a mano.

5 Conexión con el proxy externo

Los contenedores no se exponen directo a internet: quedan detrás de un servidor web existente (por ejemplo el que ya atiende siasaf.gob.mx), que debe reenviar dos rutas.

Ruta públicaDebe apuntar a
/sitickets/Contenedor frontend, puerto 8087
/sitickets/backend/api/Contenedor backend, puerto 3032, ruta /api/

Esto es así porque el frontend, cuando NO corre en localhost:4200 (modo desarrollo), arma sus llamadas a la API con esa ruta relativa fija: /sitickets/backend/api/. Si el proxy externo usa otro prefijo, hay que avisar para ajustar esa constante en el código antes de compilar.

HTTPS El certificado y el TLS los resuelve el proxy externo, no los contenedores de este sistema — ellos solo hablan HTTP puro entre sí dentro de la red del servidor.

6 Primer arranque y verificación

  1. Con SEED_ON_BOOT=true y la base vacía, el sistema siembra los catálogos (servicios, problemas, prioridades) y el padrón de usuarios internos, todos con la contraseña de SEED_PASSWORD.
  2. Entrar a https://<dominio>/sitickets/entrar y validar que cargue la pantalla de inicio de sesión.
  3. Iniciar sesión con un RFC sembrado como administrador y revisar que el menú lateral muestre todas las opciones de administración (Catálogo de servicios, Catálogo de problemas, Prioridades, Registrar usuario, Reporte de tickets, Equipos dados de baja).
  4. Registrar un ticket de prueba y confirmar que aparece en Todos los tickets y que el reloj y la asignación automática funcionan.
  5. Confirmar que backend/storage es un volumen persistente: generar un dictamen de prueba y verificar que el archivo sobrevive a un docker compose restart.

7 Mantenimiento y actualizaciones

Actualizar a una versión nueva

git pull origin main docker compose -f docker-compose.prod.yml up -d --build

Las migraciones nuevas que traiga el código se aplican solas al reiniciar el backend.

Ver logs

docker logs sitickets-backend --tail 100 -f docker logs sitickets-frontend --tail 100 -f

Respaldos

  • La base de datos propia del sistema se respalda igual que cualquier base MySQL (mysqldump programado).
  • La carpeta backend/storage (dictámenes y cédulas en PDF) debe respaldarse aparte: no vive en la base de datos.

8 Lista de verificación final
